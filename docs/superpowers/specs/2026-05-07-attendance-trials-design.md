# Module 10 — Attendance, Sessions & Trials: Design Spec

_Date: 2026-05-07_
_Status: Approved — ready for planning_

---

## Overview

Module 10 handles the **operational session lifecycle**—tracking who attended, what was covered, and the entry point for new students via Trials. It depends on Roster Assignments (Module 9) as the anchor for every session event.

Three core sub-domains:
1. **Attendance** — Marking member presence/absence for scheduled batch sessions or makeups.
2. **Session Notes** — Capturing lesson plans, topics covered (public), and per-member private observations (coach-only).
3. **Trials** — Booking trial sessions, performing assessments, and converting trials into enrollments.

**Stack:** Next.js 16.2.2 App Router · Supabase Postgres · `@supabase/ssr` · TypeScript 5

**Supabase Project ID:** `nxocuhlrldrbbltiqkqh`

---

## Chosen Approach: Assignment-anchored events

Every row in `attendance`, `session_notes`, and `trials` is anchored to a `roster_assignment_id`. 
- **Regular sessions**: The roster assignment is auto-generated by the weekly roster.
- **Makeup/Trial sessions**: A manual `roster_assignment` is created (Module 9 API) and then referenced by the attendance or trial record.

### Why this approach

- **Single Source of Truth**: By using `roster_assignment_id` as the anchor, we ensure that every session event is tied to a specific date, time, location, and coach.
- **Status-based attendance**: `AttendanceStatus` is expanded to include `trial attended` and `makeup attended`, allowing the roster view to clearly distinguish student types without separate join-heavy queries.
- **Unified Coach UX**: The coach sees a single list of "Sessions" regardless of whether the session is a regular batch, a makeup, or a trial.

## RLS Policies

### `attendance`

| Policy | Operation | Condition |
|---|---|---|
| `coach_manage_attendance` | ALL | `exists (select 1 from roster_assignments ra where ra.id = roster_assignment_id and ra.coach_id = auth.uid())` |
| `admin_all_attendance` | ALL | `jwt role in ('franchisor_admin', 'franchisee_admin')` |
| `customer_read_member_attendance` | SELECT | `member_id in (select id from members where customer_id = ...)` |

### `session_notes`

- Public notes (`topic_covered`, `homework_notes`) are READABLE by customers whose members were in that session.
- Internal notes are only READABLE by coach/admin.
- (In practice, split into two policies or filter in the API).

### `trials`

| Policy | Operation | Condition |
|---|---|---|
| `customer_own_trials` | ALL | `member_id in (select id from members where customer_id = ...)` |
| `coach_read_assigned_trials` | SELECT | `roster_assignment_id in (select id from roster_assignments where coach_id = auth.uid())` |

## API Design

### Attendance & Sessions

- `GET /api/sessions?coachId=&from=&to=`: List sessions for a coach. Joins `roster_assignments` + `batches` + `levels` + `planets`.
- `GET /api/sessions/:id/attendance`: List students (enrolled + makeup + trial) for a specific assignment.
- `PATCH /api/sessions/:id/attendance`: Bulk update attendance statuses.
- `GET /api/sessions/:id/notes`: Get session notes.
- `POST /api/sessions/:id/notes`: Create/Update session notes.
- `GET /api/sessions/:id/member-notes`: Get private member notes for the session.

### Trials

- `GET /api/trials`: List trials (filterable by memberId/locationId).
- `POST /api/trials`: Book a trial. Automatically creates a `roster_assignment` if it doesn't exist for that batch/date.
- `POST /api/trials/:id/assessment`: Save assessment + recommendations.

## Key Flows

### Marking Attendance

1. Coach opens session card → click "Mark Attendance".
2. UI calls `GET /api/sessions/:id/attendance`.
3. Coach clicks "Present" or "Absent" for each student.
4. Coach writes "Topic Covered" and "Homework".
5. Click "Save" → calls `PATCH attendance` and `POST session_notes`.

### Trial Assessment

1. Coach identifies student as a "Trial" student in the attendance list.
2. Click "Assess" button.
3. Modal: Textarea for feedback + "Recommended Level" dropdown.
4. Click "Submit" → sets `trial.status = 'completed'` and creates `trial_assessment` record.
